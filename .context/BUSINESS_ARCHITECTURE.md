# DTX 商场智能管家 — 业务逻辑架构

> 本文档从**业务**视角描述系统:这个"智能管家"大脑是怎么搭的、提供哪些业务能力、一次逛商场的全旅程如何串联。尽量用大白话讲逻辑,不涉及代码文件路径或技术栈(那些见 [ARCHITECTURE.md](./ARCHITECTURE.md))。

---

## 1. 业务定位

把一座商场里**分散、孤岛**的服务能力(导购、礼宾、客服、停车、会员、营销活动),装进**一次自然对话**。顾客不需要知道"哪个服务在哪、该用哪个入口",只管用嘴说要什么,由一个"猫 IP 智能管家"统一理解意图、调度能力、给出**可执行的结果**(一张卡、一个号、一份日程、一张券)。

管家的三重角色:
- **导购**:逛什么、吃什么、买什么、怎么安排行程。
- **礼宾**:预约、取号、停车、入会等事务办理。
- **客服**:服务台规则、退换货、红包用法、天气等答疑。

## 2. 智能体架构(管家大脑怎么转)

这一节回答几个最常被问的问题:**是不是一个"主管家"带一群"子专员"?意图识别集中在主管家,还是分散?一整圈是怎么串起来的?**

### 2.1 一句话模型:前台调度 + 业务专员

把管家想象成一家**总服务台**:

- 有一个**首席前台调度员**(主 Agent,叫 `route`)坐镇,顾客所有话都先进它这里。
- 后台坐着 **16 位业务专员**(子能力,叫 skill)各管一摊:餐饮推荐、品牌咨询、停车、入会、排队……
- 调度员的活儿不是自己解决问题,而是**听懂顾客要什么 → 把单子派给对的那位专员** → 把专员的回执(一张卡/一个号)交给顾客。
- 极少数情况前台实在判断不了该派谁,会**呼叫一个"通用客服大脑"(LLM 自由对话)**兜底,它还能现场调用专员帮忙。

> 所以是「**一个主 Agent + 多个子 skill**」的拓扑,主 Agent 负责"接客 + 路由",子 skill 负责"干活"。这是 Agent 架构里最常见、也最稳的「**路由 + 技能**」形态(技术圈叫 router-agent / skill-based agent)。

### 2.2 整体拓扑图

```
                        顾客一句话(文字)
```

### 2.3 关键认知:5 道派单关卡,有先后、不平等

主 Agent 不是"一个模型从头猜到尾",而是**按固定顺序过 5 道关卡**,前一道认领了就不往下走。这个顺序有意为之:

| 关卡 | 谁来认领 | 为什么这样设计(业务上的道理) |
|---|---|---|
| ① 在途事务 | 还没收尾的流程(停车在收车牌、预约在选档期、入会在填表、活动预约在选场次) | 一旦顾客在办某件事,中间任何短话都得让那位专员续接,**别让 LLM 重新猜打断话题**。这保证办一半的事不丢 |
| ② 短追问复用 | "换个口味""再来一家""另一家呢"这种没主语的短话 | 这种话没人名地名,靠 AI 猜十有八九猜错,所以**沿用上一轮那位专员**最稳 |
| ③ 高频确定性口令 | 七夕打卡、乐高预约、查打卡点、报出具体商品名 | 这些是**无歧义、又高频**的,直接定死路由,不浪费一次 AI 调用 |
| ④ LLM 分类器 | 其余所有 | 这是**主意图判断的主力**。把 16 位专员各自"接什么单"的说明喂给 AI,带最近几轮对话,让它点一个名字 |
| ⑤ LLM 自由对话兜底 | ④ 也判不出来 | 极少数边缘情况才轮到,它能现场用 10 个工具按钮调专员,最多来回 5 轮,出卡即停 |

> 一句话:**skill 优先,LLM 兜底**。绝大多数时候是"专员直接干活"(①②③),只有需要语义理解时才请 AI 出手(④),再不行才完全交给 AI 自由发挥(⑤)。

### 2.4 意图识别集中还是分散?

**答案:分散的,而且是"分层就近"——主入口判"归哪位专员",专员内部再判"走哪个分支"。** 不是把所有理解塞进一个地方。

两层意图识别:

```
第 1 层(主入口,集中在主 Agent):
   顾客说的是什么"大类意图" → 应该派给哪位专员(16 选 1)?
   主力 = ④ LLM 分类器;①②③ 用状态/口令兜底。

第 2 层(专员内部,分散在各 skill 里):
   进了专员之后,再判"具体走哪个子分支 / 具体参数是什么"。
   例:进了"逛吃购推荐"专员,它内部还要再判三件事——
       · 是单点推荐(只问今天吃什么 / 只想买包),
          还是 整体行程规划(想安排大半天)?
       · 如果是规划:待多久?几个人?要不要吃饭?要先去哪些店?
       · 如果是单点:餐饮、零售、还是活动推荐?
```

这就是为什么会有**多套 AI 在接力**:
- 主 Agent 的 **LLM 分类器**:只做"16 选 1",轻量,只点名字。
- **逛吃购推荐专员**(store-recommend)进了之后,还会**再调一次 AI**(`parsePlanningIntent`)专门去理解行程意图——待多久、几个人、要不要吃饭、先去哪些店,而且**要求 AI 必须给出"顾客原话证据"**才能认定同伴信息(防 AI 凭空编造"带娃",把行程人群搞错)。

> 业务上为什么要分两层?因为**"归哪个专员"是一个粗判断**,适合集中做一次;而**"这条规划具体怎么安排"是细理解**,每个专员只懂自己那一摊,放在专员内部最近、信息最全的地方做最准。就像总台只负责分诊到科室,具体怎么治交给专科医生。

### 2.5 一张单子从进到出的完整寿命

把 2.2 的拓扑换成一个**时序**视角(顾客问→管家回的一整圈):

```
顾客发话
  │
  ├─ 主 Agent 记下这句 + 翻出最近几轮对话  ← 上下文是"记忆"
  │
  ├─ 过 5 道关卡,确定派给谁(① 在途→② 短追问→③ 口令→④ 分类器→⑤ 兜底)
  │
  ├─ 对应专员接单,内部做自己的理解与判断(可能再调 AI,如行程规划)
  │     └─ 专员产出"回执":一段话 + 一张/多张卡(餐厅卡、行程卡、预约卡…)
  │
  ├─ 主 Agent 收到回执,顺手把"顾客的会员档案 / 停车信息 / 排队信息"更新回去 ← 副作用
  │
  └─ 把回执交给顾客,并在聊天里露出对应的卡片 + 下一步快捷选项("刷新排队""换个口味"…)
```

> 注意两个"暗地里"做的事,顾客感知不到但很关键:
> - **记忆**:主 Agent 始终留着最近几轮对话,所以"刚才说的那家餐厅"能被后续追问接上。
> - **回写画像**:顾客随口说的偏好("我比较喜欢美妆")、办完的事(入会成功、停车登记),会被悄悄写回档案,影响后续推荐。

### 2.6 16 位专员(子 skill)一览

这是后台全部"业务专员"。注意**能力域**和"专员"不是一一对应:有的专员很专一(只做入会),有的专员身兼多职(逛吃购一人包餐饮+零售+活动+行程规划)。

| 专员(skill) | 业务身份 | 一句职责 |
|---|---|---|
| store-recommend | 逛吃购总顾问 | 餐饮/零售/活动推荐 + **行程规划**(最复杂的专员) |
| store-consult | 品牌导购 | 某品牌在哪 / 新品 / 联系 SA |
| appointment | 奢品预约员 | 品牌专柜档期预约 |
| activity-booking | 活动预约员 | 乐高拼搭等场次预约 |
| membership | 会员顾问 | 入会全流程 + 会员咨询 |
| parking | 停车管家 | 登记 / 找位 / 收费 / 预约车位 |
| queue | 排队取号员 | 餐厅托管取号 + 进度 |
| cross-sell | 等位营销员 | 排队时长 + 交叉推券 |
| coupon | 优惠券员 | 品牌/商场券查询 |
| service-qa | 服务问答员 | 服务台规则 / 红包用法 / 天气旁支 |
| check-in | 打卡引导员 | 打卡活动 + 打卡点 |
| red-packet-usage | 红包讲解员 | 红包"碰一下"用法 |
| activity-intro | 活动介绍员 | 七夕主题介绍 |
| product-recommend | 节日送礼员 | 节日/送礼多商品推荐 |
| product-intro | 单品讲解员 | 具体商品单品介绍 |
| weather | 天气播报员 | 天气查询 |

## 3. 业务角色

| 角色 | 定位 | 与管家的关系 |
|---|---|---|
| 顾客(访客 / 会员) | 服务对象,口语化提需求 | 唯一输入源;会员态决定权益与推荐方向 |
| 智能管家(猫 IP) | 统一入口与调度中枢(主 Agent) | 理解意图 → 选专员 → 给执行结果 |
| 品牌门店 / SA | 预约、咨询的履约方 | 提供档期、专柜位置、新品、导购联系方式 |
| 商场运营 | 营销/权益/规则的供给方 | 提供活动、优惠券、会员等级、停车权益、打卡点 |

## 4. 顾客旅程主线(业务全链路)

```
                         一次逛商场的完整旅程
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ ① 到场前  │ → │ ② 到场    │ → │ ③ 逛/吃/购 │ → │ ④ 深度体验 │ → │ ⑤ 收尾    │
 └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
  · 查天气       · 停车登记     · 逛吃购推荐    · 奢品档期预约   · 打卡领券
  · 入会(享权益) · 找车位/收费   · 行程规划      · 活动场次预约   · 用红包/券
  · 了解活动/品牌 · 服务台问答   · 品牌咨询      · 餐厅排队取号   · 行程复盘
                                                              · 离场缴费
```

- 旅程是**非线性**的:顾客随时可跳回任意环节(逛着逛着想起要查停车),管家按"在途事务"(见 §2.3 关卡①)识别并续上,而非每次重头开始。
- 管家是**旅程编排者**:不仅回答单点问题,还能把多个环节编排成一份「可执行日程」(行程规划)。

## 5. 业务能力域(Capability Map)

按业务场景而非专员划分。一个域可能对应多位专员,一个专员也可能横跨多个域。

| 业务域 | 解决顾客什么问题 | 背后的专员(子 skill) | 产出物 |
|---|---|---|---|
| **逛吃购推荐域** | "我该逛啥/吃啥/买啥" | store-recommend(含行程规划) | 餐厅卡 / 品牌卡 / 活动卡 / 行程日程卡 |
| **品牌咨询域** | "某品牌在哪/有啥新品/怎么联系" | store-consult | 品牌卡(楼层/品类/亮点/SA/权益) |
| **预约服务域** | "我要预约" | appointment + activity-booking | 预约卡 / 活动预约卡 |
| **餐饮服务域** | "想吃饭,人多吗" | queue + cross-sell | 排队卡 / 优惠卡(等位久推下午茶) |
| **会员服务域** | "我要入会/会员有啥用" | membership | 入会卡 / 授权卡 / 迎新礼卡 |
| **停车服务域** | "车停哪/怎么收费/怎么预约" | parking | 停车卡 / 购物指南卡 / 预约卡 |
| **营销互动域** | "有啥福利/怎么玩" | check-in + coupon + red-packet-usage + activity-intro + product-recommend + product-intro | 打卡卡 / 优惠卡 / 红包流程卡 / 活动介绍卡 / 商品推荐卡 |
| **服务咨询域** | "商场规则/天气" | service-qa(天气旁支 weather) | 纯文本答疑(规则+天气) |

> 「行程规划」是全应用业务复杂度核心 —— 它不是一个孤立能力,而是**把推荐域里多个点织成一条时间线**,见 §7.2。

## 6. 核心业务实体与状态

业务围绕几个会随旅程演化的实体展开。每个实体有生命周期状态,管家据此判断"该续上还是该新开"(对应 §2.3 关卡① 的在途判断)。

| 业务实体 | 关键属性 | 生命周期状态 |
|---|---|---|
| 会员档案 | 姓名/性别、品类偏好、品牌偏好、会员等级 | 访客 → 授权中 → 待填表 → 偏好收集中 → 已入会 |
| 停车记录 | 车牌、车位、入场时间、对应会员等级 | 未登记 → 已登记 → (预约中) → 待缴费 |
| 排队号 | 餐厅、号序、当前进度 | 未取号 → 取号 → 等位 → 即将就绪 → 就绪 |
| 品牌预约 | 品牌、档期/场次、人数 | 待选档期 → 已选 → 已预约 |
| 行程日程 | 时长预算、同伴、正餐/茶歇配额、时段、锁定项 | 待定时长 → 生成中 → 已校验 → 回退文本 |
| 优惠券/红包 | 品牌/商场通用、场景(等位/迎新/打卡) | 待领 → 已领 → (可用) |

**会员档案是"暗线"**:偏好(品类/品牌/人群)驱动推荐与行程筛选,会员等级驱动停车权益;顾客全程感知不到"系统在用档案",但每次推荐都已被画像过滤(对应 §2.5 的"回写画像")。

## 7. 关键业务流程

### 7.1 入会流程(会员服务域)

```
授权(获取身份) → 表单信息提取(姓名/性别/偏好) → 偏好补全(品类/品牌/人群) → 入会成功 → 迎新礼
```
- 业务意义:入会不是"填个表",而是**构建后续所有个性化推荐的基座**;偏好收得越准,逛吃购与行程越贴。
- 中断可恢复:任一环节顾客岔开话题去问别的,管家能记住"入会进行到第几步",稍后续上(主 Agent 关卡① 把单子钉回 membership 专员)。

### 7.2 行程规划流程(逛吃购推荐域 · 核心)

这是管家区别于"问答机器人"的所在:**把顾客的一句模糊需求,编排成一份带时段的可执行日程**。也是前面 §2.4 提到的"第 2 层意图识别"的主舞台——进了 store-recommend 专员后又一次调 AI 做细理解。

```
顾客意图(可能很模糊:"带娃来大半天")
   │
   ├─ 意图理解(主) :是否要规划?待多久?几个人?想干啥?要不要吃饭?(又一次 AI 调用)
   │                 · 同伴信息必须附"顾客原话证据",代码校验证据真伪后才采信
   ├─ 可靠性兜底    :用规则补全被漏掉的时长/意图信号(两者取并集)
   │
   ├─ 时间预算推导  :全天→2正餐 / 半天→1正餐 / 仅晚间→1餐 / 不吃→0餐
   │                 (配额由时长推导,不写死"一天最多1顿")
   ├─ 候选筛选      :按会员画像+人群打分排序,每品类限数,保证多样性
   ├─ 日程生成      :拼成带时段的"可执行日程"(餐间隔≥3h,正餐后不接茶歇)
   └─ 合规校验      :串吃/堆砌/品类集中/时段空洞/人群不符 → 不通过则重生成(≤2次),再不行回退纯文本
```

**业务约束(都是历史踩坑固化下来的规则)**:
- 同伴信息必须**有原话证据**,防止凭空编造"带娃"(编错人群会让行程全错)。
- 上一轮管家在问时长、本轮顾客只回了时间,仍判定为"在做规划"(反问闭环)。
- 给顾客的是**可执行日程**,不是一堆候选清单堆在卡里。
- 行程要体现人群(亲子/情侣/独逛)与品类多样性,不能一天都是美妆。

### 7.3 预约流程(预约服务域)

两类预约,均为**信息收集状态机**(顾客分多次提供信息,管家逐步收齐再下单),靠主 Agent 关卡① 续接中断:
- 奢品专柜档期预约:选品牌 → 看档期 → 选档期 → 确认。
- 活动场次预约(乐高拼搭):选活动 → 选周六日场次 → 人数 → 确认。

### 7.4 餐饮排队 + 交叉营销(餐饮服务域)

```
取号 → 进度自动推进(等位 → 即将就绪 → 就绪,就绪时主动提醒) → 等位过久? 推下午茶券(交叉营销)
```
- 业务亮点:排队托管期间,管家**主动**在关键节点提醒,并在等待变长时把"等待焦虑"转化为"邻店消费"——这是商场把客流从餐厅溢出到其他业态的营销动作。

### 7.5 停车流程(停车服务域)

登记车牌 → 找到车位 → (查询状态) → 按会员等级享停车权益 → 离场缴费指引。会员等级直接决定停车优惠,与会员档案联动。

### 7.6 打卡 / 领券(营销互动域)

打卡活动(完成可领券)→ 优惠券(品牌专属 / 商场通用)→ 红包"碰一下"用法。把"逛"与"薅羊毛"绑定,提升到店频次与停留时长。

## 8. 业务规则与约束总览

| 约束类别 | 规则 | 业务目的 |
|---|---|---|
| 个性化 | 推荐与行程按会员画像(品类/品牌/人群)过滤 | 不推无关,提升转化 |
| 权益联动 | 停车优惠、专属券随会员等级 | 入会的存量价值 |
| 反编造 | 同伴/人群信息需有顾客原话支撑(证据 + 代码校验) | 防行程因错误人群全盘错位 |
| 可执行 | 行程给"带时段的日程"而非候选堆砌 | 顾客照着走就行 |
| 多样性 | 行程单品类限量、餐饮按预算配额 | 避免一天同质化 |
| 编排安全 | 日程经"超餐/堆砌/空洞/人群"校验,不过则重生成 | 不会给出走不通的安排 |
| 中断可续 | 在途事务(停车/预约/入会/排队)可被岔开话题打断后续上 | 符合真实逛商场节奏 |
| 等位转化 | 排队久等 → 推邻业态券 | 把餐厅溢出客流导向其他店 |
| skill 优先 | skill 能定的不上 LLM,分类器能定的不进自由对话兜底 | 稳、省、可解释 |
